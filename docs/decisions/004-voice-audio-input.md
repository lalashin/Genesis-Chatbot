# 004. 음성 입력을 st.chat_input 녹음 + Gemini 받아쓰기로 교체

- **날짜**: 2026-10-07
- **상태**: 채택 (003을 대체)

## 배경
- 브라우저 내장 음성 인식(Web Speech API)은 앱의 주제를 몰라 차량 용어를 일상어로 알아들었다.
  실제 사용 중 "차체" → "자체" 오인식 발생.
- Chrome의 Web Speech API에는 단어 힌트를 줄 방법이 없다.
- 음성 코드가 iframe 밖의 부모 페이지 DOM을 조작하는 구조라, 이미 두 번(003) 버그가 났고 Streamlit 버전이 바뀌면 다시 깨질 위험이 있다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| Web Speech API 유지 | 무료, 말이 끝나면 자동 감지 | 용어 힌트 불가, 구조가 불안정 |
| **`st.chat_input(accept_audio=True)` + Gemini 받아쓰기** | Streamlit 기본 기능(JS 없음), 프롬프트로 용어 힌트, 녹음 1회 = 질문 1개 | 질문마다 Gemini 호출 1회 추가, 녹음 정지 버튼을 눌러야 함 |
| 전용 STT 서비스(Google Cloud STT 등) | 정확도·속도 | 별도 계정·과금, 실습 데모에 과함 |

## 결정
`st.chat_input(accept_audio=True)`로 녹음하고, `voice.transcribe()`가 Gemini에 녹음과 함께
"제네시스 차량 매뉴얼 질문"이라는 맥락과 차량 용어 목록(약 50개)을 줘서 받아쓴다.
받아쓴 문장은 기본적으로 **입력창에 넣어 확인 후 전송**한다(사이드바에서 바로 전송으로 변경 가능).
> 2026-10-07 변경: 기본값을 바로 전송 + 음성 질문 표시로 바꿈 → [006](006-voice-auto-send.md)

## 이유 (측정)
TTS 합성 음성 10문장으로 비교 (`eval/run_voice_eval.py`, 결과: `docs/eval/2026-10-07_voice.md`):

| | 정확히 받아쓴 문장 |
|---|---|
| 힌트 없음 | **6/10** — "**자체**에 흠집이…", "**자율** 유지 보조…", "**HD** 디스플레이…" |
| 용어 힌트 사용 | **10/10** — "**차체**에 흠집이…", "**차로** 유지 보조…", "**헤드업** 디스플레이…" |

사용자가 실제로 겪은 "차체 → 자체" 오인식이 힌트 없는 받아쓰기에서 그대로 재현되었고, 용어 힌트로 해결되었다.

구현 중 발견: Streamlit 가이드 예제처럼 `st.chat_input`을 만든 뒤 `st.session_state[key]`를 바꾸면
`StreamlitWidgetAlreadyInstantiatedError`가 난다. 받아쓴 문장을 `pending_input`에 저장했다가
다음 실행에서 입력창을 만들기 **전에** 넣는 방식으로 해결 (AppTest로 검증).

## 영향
- 부모 페이지 DOM을 조작하던 JavaScript(약 240줄)와 온보딩 토글의 마이크 권한 선요청 로직을 제거했다.
- 질문당 Gemini 호출이 1회 늘어난다. `gemini-3.5-flash-lite` 무료 한도는 **분당 15회**이므로
  음성 질문 기준 분당 4~5개 정도가 한계다 → 한도 초과 시 안내 문구로 대응(agent.friendly_error).
- TTS 음성은 사람 목소리보다 또렷하므로, 실제 마이크로 추가 확인이 필요하다.
